# Ticket Support — Rust/Axum Backend

A ticket-support system with JWT authentication, refresh-token rotation,
per-IP rate limiting, and AES-256-GCM encryption of all message content.

---

## Stack

| Crate | Purpose |
|---|---|
| Axum 0.7 | HTTP framework |
| sqlx 0.8 | Async SQLite driver |
| Tokio 1 | Async runtime |
| jsonwebtoken 9 | JWT access tokens (HS256) |
| argon2 0.5 | Password hashing (argon2id) + key derivation |
| aes-gcm 0.10 | Thread body encryption (AES-256-GCM) |
| bcrypt 0.15 | Legacy hash verification only |
| rand 0.8 | Cryptographically secure RNG |

## Security Design

This section explains the reasoning behind the cryptographic choices — not just
what was used, but why.

### AES-256-GCM for message body encryption

Thread entry bodies are encrypted with AES-256-GCM rather than a simpler mode
like AES-CBC because GCM is an **authenticated encryption** scheme. It protects
against two distinct threats simultaneously:

- **Confidentiality** — an attacker who reads the database cannot recover the
  plaintext without the key.
- **Integrity** — an attacker who writes to the database cannot flip bits in a
  ciphertext entry and have those flipped bits silently accepted as valid
  plaintext. Every decryption attempt verifies a 128-bit authentication tag
  computed over both the nonce and the ciphertext. If a single byte has been
  tampered with, decryption fails with an explicit error rather than returning
  corrupted data.

AES-CBC provides only confidentiality. A padding-oracle or bit-flipping attack
against CBC can produce chosen-plaintext outputs that the application silently
decrypts into attacker-controlled values. GCM closes that entire class of
attack.

Each message uses a **unique 12-byte nonce** generated by `OsRng`. Reusing a
nonce under the same key would break both confidentiality and integrity for GCM,
so per-entry randomness is non-negotiable. The nonce is stored alongside the
ciphertext in `thread_entries.body_nonce`.

### Argon2id for passwords and key derivation

Argon2id was chosen for both password hashing (`services/auth.rs`) and
derivation of the AES encryption key from the `.env` passphrase (`crypto.rs`).

**Why Argon2id over bcrypt or PBKDF2?**

Argon2id is the winner of the 2015 Password Hashing Competition, specifically
designed to resist the hardware attacks that make older KDFs weak:

- **Memory-hardness** — Argon2id fills a configurable amount of RAM (64 MiB
  for key derivation here; OWASP-recommended defaults for passwords). Filling
  that memory is inherently sequential; an attacker cannot parallelise across
  thousands of GPU cores or custom ASICs the way they can with bcrypt, because
  each core needs its own copy of the working memory.
- **GPU resistance** — GPUs have enormous parallelism but limited per-core
  memory bandwidth. Memory-hard algorithms invert this advantage entirely:
  cracking speed is bounded by memory, not compute.
- **ASIC resistance** — The same memory requirement makes custom cracking
  silicon prohibitively expensive to build compared with SHA-256 or bcrypt
  ASICs.

The `id` in Argon2**id** refers to a hybrid construction that combines
Argon2i (side-channel resistance) and Argon2d (GPU resistance), making it the
recommended variant for password hashing where side-channel attacks are a
concern (e.g. when the hash function and the attacker share hardware).

**Parameter choices**

Two call sites, two parameter sets:

| Site | Memory | Iterations | Parallelism |
|---|---|---|---|
| Password hashing (`hash_password`) | 19 MiB (OWASP default) | 2 | 1 |
| Key derivation (`derive_key`) | 64 MiB | 3 | 1 |

Key derivation uses higher parameters because it runs once at startup with no
latency requirement, so there is no reason not to make it as expensive as
hardware comfortably allows.

Password hashing uses OWASP-recommended defaults: 19 MiB and 2 iterations are
calibrated so that each verification attempt requires that much memory and
wall-clock time on the server. The consequence for an attacker trying to crack a
leaked hash is direct — **each guess costs 19 MiB of RAM, held for the full
duration of the computation**. A GPU with 24 GB of VRAM can run at most ~1,260
parallel guesses at that memory footprint, compared with millions of parallel
SHA-256 invocations. A purpose-built cracking cluster capable of 10⁹ bcrypt
guesses per second is reduced to tens of thousands of Argon2id guesses per
second per node, because memory bandwidth — not floating-point throughput — is
the binding constraint. The parameters were chosen to require significant memory
per guess, making large-scale brute force expensive even with dedicated hardware,
while keeping login latency acceptable for a low-concurrency deployment where
only one or a handful of users authenticate at a time.

For **key derivation**, the same principle applies with more force: a static
passphrase stored in `.env` has only the entropy a human chose. Running Argon2id
at 64 MiB and 3 iterations makes an offline dictionary attack against a leaked
passphrase two to three orders of magnitude more expensive than the equivalent
wall-clock cost in PBKDF2-HMAC-SHA256.

### SHA-256 hashing of refresh tokens

Refresh tokens are stored in the `sessions` table as `SHA-256(raw_token)`, not
as the raw value the client holds in its cookie.

The threat this defends against is a **database breach without a corresponding
application breach**. SQLite databases are single files; a misconfigured backup,
a path-traversal vulnerability, or direct filesystem access could expose the
entire `sessions` table. If the raw tokens were stored, every active session
would be immediately hijackable — the attacker can copy any token into a cookie
and the server has no way to distinguish it from the legitimate holder.

With hashes stored instead:

- A leaked database row gives an attacker a 64-character hex string from which
  the 32-byte raw token cannot be feasibly reversed (SHA-256 is a one-way
  function).
- The raw token travels only over the wire (HTTPS) and lives only in the
  browser's httpOnly cookie. It is never persisted anywhere the server writes.

The same pattern is used for password storage — bcrypt/argon2id ensures that
a leaked `users` table does not hand an attacker usable credentials without a
costly offline attack. The session table applies the analogous principle to
tokens.

## Setup

### 1. Configure `.env`

```bash
cp .env.example .env
```

Edit `.env` and fill in every value. Generate strong secrets:

```bash
openssl rand -hex 32   # → JWT_SECRET
openssl rand -hex 16   # → ENCRYPTION_SALT (set once, never change)
```

### 2. Run

```bash
cargo run -p backend
```

Server listens on `BIND_ADDR` (default `127.0.0.1:3000`).

On first run:
1. Creates `data/support.db` and runs migrations
2. Creates `uploads/` for file attachments
3. Derives the AES-256-GCM key (~2 s — Argon2id with 64 MiB)
4. Cleans up any expired/revoked sessions
5. Seeds `desk@local` / `changeme` (warns if still default)

## Environment Variables

| Variable | Required | Default | Description |
|---|---|---|---|
| `DATABASE_URL` | no | `sqlite://data/support.db` | SQLite file path |
| `BIND_ADDR` | no | `127.0.0.1:3000` | TCP bind address. Set `0.0.0.0:3000` to expose on all interfaces (e.g. behind a reverse proxy). |
| `JWT_SECRET` | **yes** | — | HS256 signing key, ≥ 32 bytes. Server panics at startup if shorter. Generate: `openssl rand -hex 32` |
| `ACCESS_TOKEN_TTL_SECS` | no | `900` | Access token lifetime (15 min) |
| `REFRESH_TOKEN_TTL_SECS` | no | `604800` | Refresh token lifetime (7 days) |
| `COOKIE_SECURE` | no | `true` | Set `; Secure` flag on the refresh cookie. Set `false` only for plain-HTTP local dev. **Must be `true` in any HTTPS deployment.** |
| `ENCRYPTION_PASSPHRASE` | **yes** | — | Passphrase for AES key derivation (min 16 chars) |
| `ENCRYPTION_SALT` | **yes** | — | Hex-encoded random salt, **fixed for the lifetime of the database**. Generate once: `openssl rand -hex 16` |

---

## ⚠ Encryption Key Warning

> **`ENCRYPTION_PASSPHRASE` and `ENCRYPTION_SALT` are the only way to decrypt
> stored thread message bodies. If either value is lost or changed after the
> first run, every thread entry in the database is permanently unrecoverable.
> There is no recovery path.**
>
> - Back up `.env` securely and **separately** from the database file.
> - Never commit `.env` to version control (it is in `.gitignore`).
> - Never change `ENCRYPTION_SALT` after data has been written.
> - The `data/` directory and `uploads/` directory are also in `.gitignore` —
>   back them up separately.

## Auth Flow

```
POST /auth/login
  → { access_token }  +  Set-Cookie: refresh_token=…; HttpOnly; Path=/auth[; Secure]

POST /auth/refresh   (browser sends cookie automatically)
  → { access_token }  +  rotated refresh cookie
  → replayed rotated token → ALL sessions deleted (theft detection)

POST /auth/logout
  → 204  +  Max-Age=0 cookie (cleared)
```

Access tokens expire after `ACCESS_TOKEN_TTL_SECS`. Call `/auth/refresh` before
expiry. `/auth/login` and `/auth/refresh` are rate-limited to 5 req/s per IP
with a burst of 10.

## Ticket Lifecycle

```
[open] ──(desk: acknowledge)──▶ [acknowledged] ──(desk: close)──▶ [closed]
  │                                                                    │
  └────────────────── no direct close allowed ────────────────────────┘
                    all transitions enforced server-side
                    in a single isolated module (ticket_status.rs)
                    — status cannot be changed anywhere else
```

| From | Action | To | Who |
|---|---|---|---|
| `open` | acknowledge | `acknowledged` | desk only |
| `acknowledged` | close | `closed` | desk only |
| any other | — | — | `400 Bad Request` |

Skipping `acknowledged` and closing an `open` ticket directly is not permitted.
This is intentional: the two-step flow gives desk agents a documented
acknowledgement point before resolution, and prevents accidental instant-closure
of tickets that have not been reviewed.

All transition logic lives exclusively in `src/ticket_status.rs::transition()`.
No other file in the codebase is able to change a ticket's status — the DB write
function `db::tickets::update_status` is only ever called from the two service
functions (`transition_ack`, `transition_close`) that go through
`ticket_status::transition` first. Bypassing the state machine is a compile-time
impossibility without modifying that module.

## curl Examples

Replace `TOKEN` with the JWT from `/auth/login`.
Replace `TICKET_ID` and `CLIENT_ID` with real UUIDs.

### Auth

**Login**
```bash
curl -sc cookies.txt -X POST http://localhost:3000/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"email":"desk@local","password":"changeme"}'
# → { "access_token": "eyJ..." }
```

**Refresh access token**
```bash
curl -sb cookies.txt -c cookies.txt -X POST http://localhost:3000/auth/refresh
```

**Logout**
```bash
curl -sb cookies.txt -X POST http://localhost:3000/auth/logout
```

### Tickets

**List**
```bash
curl http://localhost:3000/tickets -H 'Authorization: Bearer TOKEN'
```

**Create**
```bash
curl -X POST http://localhost:3000/tickets \
  -H 'Authorization: Bearer TOKEN' \
  -H 'Content-Type: application/json' \
  -d '{"title":"Cannot log in","description":"Getting 401 every time."}'
```

**View ticket + thread** *(bodies are decrypted transparently)*
```bash
curl http://localhost:3000/tickets/TICKET_ID -H 'Authorization: Bearer TOKEN'
```

**Acknowledge** *(desk only — open → acknowledged)*
```bash
curl -X PATCH http://localhost:3000/tickets/TICKET_ID/ack \
  -H 'Authorization: Bearer TOKEN'
```

**Close** *(desk only — acknowledged → closed)*
```bash
curl -X PATCH http://localhost:3000/tickets/TICKET_ID/close \
  -H 'Authorization: Bearer TOKEN'
```

### Messages

**Post text message** *(body encrypted before storage)*
```bash
curl -X POST http://localhost:3000/tickets/TICKET_ID/message \
  -H 'Authorization: Bearer TOKEN' \
  -F 'body=Here is my reply.'
```

**Post with attachment** *(max 10 MiB)*
```bash
curl -X POST http://localhost:3000/tickets/TICKET_ID/message \
  -H 'Authorization: Bearer TOKEN' \
  -F 'body=See attached.' \
  -F 'file=@/path/to/screenshot.png'
```

Files are saved to `./uploads/<ticket_id>/`. The directory is not served.
